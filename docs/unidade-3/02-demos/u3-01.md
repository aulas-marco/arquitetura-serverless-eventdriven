# U3-LAB01 — Produtor Kinesis com roteamento por clienteId

Primeiro laboratório da Unidade 3. Cria um stream Kinesis de 4 shards e publica eventos de suporte usando o `clienteId` como PartitionKey — demonstrando que a mesma chave sempre aterra no mesmo shard e que clientes distintos se distribuem entre shards diferentes.

## 1. Objetivos de aprendizagem (Bloom)

- **Descrever** a anatomia de um Kinesis Data Stream: shards, PartitionKey e sequenceNumber.
- **Explicar** por que o hash da PartitionKey determina o shard de destino e garante ordenação por chave.
- **Identificar** a diferença entre `PutRecord` (um registro) e `PutRecords` (lote) e por que o lote é preferível.
- **Diferenciar** Kinesis (ordenação por chave, retenção, reprocessamento) de SQS (fila discreta, sem ordenação por chave).

Base conceitual: [Streaming e Kinesis](../01-fundamentos/1-streaming-e-kinesis.md).

## 2. Motivação

Tickets de suporte do mesmo cliente devem ser processados em ordem de chegada — senão um "problema resolvido" pode chegar antes do "ticket aberto". O `clienteId` como PartitionKey faz exatamente isso: todos os eventos de `cli-001` caem no mesmo shard, em ordem. Clientes diferentes podem ir para shards diferentes, aumentando o throughput total sem sacrificar a ordenação por cliente.

## 4. Topologia

```mermaid
flowchart LR
    C[curl] -->|POST /eventos\narray JSON| H{{ProdutorFunction}}
    H -->|PutRecords\nPartitionKey=clienteId| K[(Kinesis\nu3lab01-eventos-suporte\n4 shards)]
    H -->|200 publicados[]\nshardId + sequenceNumber| C
```

O ponto a **identificar**: a HTTP API recebe o array de eventos; o Lambda os converte em registros Kinesis com `PartitionKey=clienteId` e chama `PutRecords`. A resposta inclui o `shardId` em que cada registro aterrou — o script usa isso para provar o roteamento.

## 5. Código anotado

`suporte.py` é puro — sem boto3, testável offline:

```python
def montar_evento(dados):
    if "clienteId" not in dados:
        raise EventoInvalido("clienteId obrigatório")
    if "mensagem" not in dados:
        raise EventoInvalido("mensagem obrigatória")
    return {"clienteId": dados["clienteId"], "mensagem": dados["mensagem"]}

def montar_registro(evento):
    # A PartitionKey é o clienteId: fixa o shard e garante ordenação por cliente
    return {
        "Data": json.dumps(evento).encode("utf-8"),
        "PartitionKey": evento["clienteId"],
    }
```

`produtor.py` orquestra:

```python
def lambda_handler(event, context):
    corpo = ler_corpo(event)
    eventos = [montar_evento(e) for e in (corpo if isinstance(corpo, list) else [corpo])]
    registros = [montar_registro(e) for e in eventos]
    resp = kinesis.put_records(StreamName=STREAM, Records=registros)
    # devolve shardId + sequenceNumber de cada registro para o caller ver o roteamento
    publicados = [
        {**e, "shardId": r["ShardId"], "sequenceNumber": r["SequenceNumber"]}
        for e, r in zip(eventos, resp["Records"])
        if "ErrorCode" not in r
    ]
    return {"statusCode": 200, "body": json.dumps({"publicados": publicados})}
```

## 6. Rodar e observar

```bash
make deploy-produtor    # implanta u3lab01-produtor (~2min)
make produtor           # publica 7 eventos e mostra o roteamento
```

Saída esperada:

```
== publicar 7 eventos (cli-001 x3, cli-002 x2, cli-003 x2) ==

  clienteId  ->  shardId                         (seq)
  cli-001   ->  shardId-000000000001  4959033827...
  cli-002   ->  shardId-000000000003  4959033827...
  cli-001   ->  shardId-000000000001  4959033828...
  cli-003   ->  shardId-000000000000  4959033827...
  cli-002   ->  shardId-000000000003  4959033828...
  cli-001   ->  shardId-000000000001  4959033829...
  cli-003   ->  shardId-000000000000  4959033828...

  resumo por cliente:
    cli-001: 1 shard(s) -> OK, sempre o mesmo (ordem garantida)
    cli-002: 1 shard(s) -> OK, sempre o mesmo (ordem garantida)
    cli-003: 1 shard(s) -> OK, sempre o mesmo (ordem garantida)
  shards distintos usados pelos 3 clientes: 3
  ✓ mesma chave -> mesmo shard -> ordenação por cliente
```

Leitura: `cli-001` sempre vai para `shardId-000000000001`; `cli-002` para `shardId-000000000003`. O shard exato depende do hash MD5 da chave e do número de shards — não é configurável, mas é **determinístico**: a mesma chave sempre vai para o mesmo shard.

## 7. Pontos de atenção

| Sintoma | Causa | O que saber |
|---------|-------|-------------|
| Dois clientes no mesmo shard | O hash pode colidir | Normal. Shards distintos para clientes distintos é probabilístico, não garantido. |
| Um shard recebe muito mais eventos | PartitionKey concentrada (ex.: todos os eventos têm a mesma chave) | Hot shard. Diversifique a PartitionKey ou use shard splitting. |
| sequenceNumbers não são sequenciais inteiros | O sequenceNumber é opaco, não um contador | Use-o só para ordenar, nunca para contar ou iterar. |
| Eventos sumiram após 24h | Retenção configurada em 24h | Aumente `RetentionPeriodHours` no template para o seu caso de uso. |

## 8. Checklist de compreensão

- [ ] Sei por que `PutRecords` (lote) é preferível a `PutRecord` (unitário) em termos de custo e throughput.
- [ ] Diferencio o sequenceNumber (ponteiro de posição) do número de sequência lógico do event store.
